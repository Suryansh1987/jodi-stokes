# 4. Registration Email Delivery

Status: Not Started  
Depends On: Task 3

## Goal

Make valid program registrations send one server-side email to Jodi and provide accurate loading, success, and failure states without storing leads.

## Context

- The project is Next.js `16.2.9` App Router with no API routes, server actions, email package, database, or environment convention.
- `CoachingSection` is currently a client component with a local `onSubmit` handler, so a small JSON `POST` endpoint requires less form restructuring and is straightforward to mock in Playwright.
- Next.js 16 local docs permit Route Handlers under `app/**/route.ts`; `POST` handlers are not cached.
- The app is not configured as a static export, but the actual production host is unknown and must support server execution.
- Resend's official API/Next.js guidance supports server-side sending with an API key and requires a verified sender domain for production recipients.

## Files / Areas Likely Involved

- Create `app/api/program-registration/route.ts`.
- Create a small server-only email helper under `lib/` if it keeps provider code out of the handler.
- Registration form component created/refactored in Task 3.
- `lib/content/programs-products.ts` for program ID allowlisting.
- `package.json` and `package-lock.json` for the official `resend` package, if provider approval is confirmed.
- `.gitignore` and a secret-free `.env.example` documenting required variables.
- `test/home.spec.ts` or a focused registration spec under `test/`.

## Required Changes

- Implement a `POST` Route Handler that accepts only the registration fields from Task 3.
- Validate and normalize all values server-side: required fields, email shape, reasonable maximum lengths, stable allowlisted program ID, optional message, and acknowledgement equal to true.
- Reject malformed/oversized payloads with a generic safe `400` response before attempting email delivery.
- Add a visually hidden honeypot field and silently accept/drop bot-filled submissions or return a generic success without sending. Do not add database-backed rate limiting for this small first version.
- Send to a server-only configured recipient that is set to `jodi@jodistokes.com` in production configuration.
- Use a verified configured sender. Put the registrant email in `replyTo`; never use untrusted user input as the sender address.
- Send a concise plain-text email containing name, email, phone, canonical program name, optional message/goals, and acknowledgement status. Plain text avoids unnecessary template architecture and HTML escaping risk.
- Return minimal JSON success/error responses without provider internals or secrets.
- Do not log registration payloads or sensitive personal data. Log only a provider/request correlation identifier or sanitized failure category when needed.
- Keep `RESEND_API_KEY`, sender, and recipient configuration server-only with no `NEXT_PUBLIC_` prefix.
- Update `.gitignore` to ignore `.env*` while allowing `.env.example`; never commit real values.
- Update the client form to prevent duplicate submission while pending, show accessible loading/success/failure states, clear fields only after confirmed success, and retain user input on failure.
- Use an `AbortController`/reasonable timeout only if needed to prevent an indefinitely pending client request; keep retry behavior user-controlled.
- Mock the `/api/program-registration` request in browser tests for deterministic loading, success, and failure UI. Do not send real email in automation.

## Explicit Non-Goals

- No database, lead history, CRM, queue, webhook processing, customer confirmation email, newsletter subscription, calendar, payment, account, or admin UI.
- No collection or transmission of medical history.
- No secrets in source, JSON content, browser bundles, test artifacts, or tracker evidence.
- Do not silently report success when a real non-honeypot provider call fails.

## Data / Client Requirements

- Recipient is `jodi@jodistokes.com`.
- Client must approve Resend or select another provider, create the account/API key, verify a sending domain, and provide the approved sender address.
- Confirm the production hosting platform supports Next.js server Route Handlers and environment variables.
- A registrant confirmation email is not currently required; do not add one without approval.

## Edge Cases

- Missing provider configuration: return a generic unavailable/failure state and keep the submitted form values; never expose which variable is missing.
- Unknown/tampered program ID: reject it rather than emailing the submitted label.
- Provider timeout/error: return failure and allow deliberate retry.
- Double click: disable while pending so one browser interaction produces one request.
- Optional message absent: email should clearly show it was not provided without inserting fake text.
- Honeypot filled: do not send and do not reveal bot-detection rules.

## Verification

- Test browser loading, success, and failure states with Playwright route interception.
- Test that success clears appropriate fields and failure retains them.
- Use Playwright/API request context to assert invalid payloads and false acknowledgement return `400` before provider access.
- Verify an unknown program ID is rejected.
- Verify no medical fields or API secrets appear in the client bundle/rendered HTML.
- With approved staging credentials only, perform one documented manual smoke submission to a controlled recipient before launch; never make this part of automated tests.
- Run `npm run lint`, `npm run build`, focused `npm run test:e2e`, and `git diff --check`.

## Completion Criteria

- Valid submissions can email Jodi through server-only provider code.
- Invalid/tampered requests do not send.
- The client accurately represents pending, success, and failure.
- Secrets and PII handling follow the constraints above.
- Automated tests are deterministic and make no real provider calls.
